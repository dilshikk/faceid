# Техническое задание и архитектура проекта Bot Control Center

**Версия документа:** 1.0
**Дата:** 12 октября 2026 г.
**Размещение:** текущий VPS
**Интерфейсы:** веб-панель и Telegram Admin Bot
**Главный приоритет:** мониторинг, статусы, логи и уведомления

## Назначение

Единая система для наблюдения за состоянием фоновых сервисов на VPS,
просмотра системных журналов, регистрации инцидентов и отправки
уведомлений администратору. Проект не должен нарушать работу существующих
приложений.

## 1. Цели и границы проекта

Bot Control Center (BCC) — самостоятельное приложение мониторинга,
подключаемое к уже работающему VPS. Оно не заменяет существующие боты,
базы данных или систему управления процессами.

### Цели первой версии

- Отображать все разрешённые systemd-службы в одном интерфейсе.
- Показывать реальный статус процесса, время последнего перехода
  состояния и доступные сведения об uptime.
- Предоставлять централизованный просмотр логов с фильтрами по сервису,
  периоду и уровню.
- Создавать инциденты при подтверждённых сбоях и уведомлять
  администратора через Telegram.
- Отображать CPU, RAM, использование диска, uptime VPS и доступность
  PostgreSQL.
- Сохранять историю статусов и важных событий для анализа сбоев.
- Обеспечить отдельные права доступа и аудит действий пользователей.

### Вне рамок MVP

- Редактирование кода существующих ботов и управление их бизнес-логикой.
- Автоматическое развёртывание из GitHub и автоматический откат версий.
- Произвольное выполнение shell-команд из веб-интерфейса или Telegram.
- Автоматический перезапуск рабочих ботов без отдельно согласованной
  политики.

> Ключевой принцип: отказ BCC не должен останавливать или изменять работу
> отслеживаемых приложений.

## 2. Исходная инфраструктура

Перечень, известный на момент подготовки документа. Перед внедрением
необходимо проверить фактическое состояние служб, конфигураций, портов и
каталогов.

| Сервис | Предполагаемое назначение |
|---|---|
| mado-bot.service | MADO HR Telegram Bot |
| invitebot.service | InviteBot |
| bkbot.service | BKBot |
| tgbot.service | TG iBot |
| Nginx | Веб-сервер и reverse proxy |
| PostgreSQL | Базы данных существующих проектов |
| PM2 | Управление некоторыми Node.js-приложениями |

BCC должен поддерживать реестр разрешённых служб и возможность добавлять
новые службы после проверки. Нельзя автоматически предоставлять доступ ко
всем процессам и системным журналам.

## 3. Архитектура и стек

Система строится как модульное приложение с тремя независимыми
процессами: API, worker мониторинга и Telegram Admin Bot.

| Компонент | Технология / ответственность |
|---|---|
| Frontend | React, TypeScript, Vite, Tailwind CSS |
| Backend API | Python, FastAPI, Uvicorn |
| Worker | Асинхронный сбор статусов, метрик и обработка инцидентов |
| База BCC | Отдельная PostgreSQL DB, SQLAlchemy, Alembic |
| Системные статусы | systemd D-Bus или безопасные команды с фиксированными аргументами |
| Логи | journald / journalctl с ограниченным доступом |
| Telegram | aiogram 3, allowlist Telegram ID |
| Веб-доступ | Nginx, HTTPS, backend на localhost |

### Поток данных

- Worker опрашивает разрешённые источники через настроенный интервал.
- Backend нормализует результаты и отличает active, inactive, failed,
  activating и unknown.
- Изменения статусов и важные события записываются в отдельную БД BCC.
- Incident manager объединяет повторяющиеся ошибки и управляет состоянием
  инцидентов.
- Web Dashboard получает данные через REST API; Telegram Admin Bot
  использует тот же сервисный слой.
- При сбое источника мониторинга система показывает unknown/error
  проверки, а не ложный статус «работает».

> Статус systemd сам по себе не доказывает, что Telegram-бот отвечает.
> Для проверки работоспособности приложения следует предусмотреть
> heartbeat или отдельный health check.

## 4. Функциональные требования

### 4.1. Главная панель

- Количество служб по состояниям и время последней успешной проверки.
- CPU, RAM, использование диска и uptime VPS.
- Список последних инцидентов и ошибок.
- Состояние PostgreSQL и доступность Telegram API.
- Состояние компонентов самого BCC.

### 4.2. Карточка сервиса

- Название, systemd unit, статус, PID при наличии, время последнего
  перехода состояния.
- Доступные сведения о последнем запуске и перезапусках.
- Просмотр последних 100–500 строк логов с пагинацией и лимитами.
- Фильтрация по времени, уровню и ключевым словам.
- История статусов и связанные инциденты.

### 4.3. Центр логов

- Единая лента с временной меткой, источником, службой и уровнем.
- Поиск и фильтры; безопасный просмотр traceback в пределах заданного
  лимита.
- Маскирование токенов, паролей, cookie и других секретов.
- Полные журналы остаются в journald; в БД BCC сохраняются только важные
  выбранные события.

### 4.4. Telegram Admin Bot

| Команда | Назначение |
|---|---|
| /start | Проверка авторизации |
| /status | Сводка по сервисам |
| /services | Список отслеживаемых служб |
| /service mado-bot | Детали указанной службы |
| /logs mado-bot | Последние ошибки разрешённой службы |
| /incidents | Открытые инциденты |
| /server | CPU, RAM, диск, uptime |
| /silence | Временно отключить определённый тип уведомлений |
| /help | Справка |

Все команды проверяют Telegram ID на сервере. Сообщения должны быть
краткими и не содержать секретов или полных чувствительных traceback.

## 5. Инциденты и уведомления

- Настраиваемый интервал проверки для каждой службы, рекомендуемое
  стартовое значение — 15 секунд.
- Подтверждение сбоя после заданного числа неуспешных проверок или
  задержки, чтобы избежать ложных тревог.
- Дедупликация по службе и fingerprint инцидента.
- Ограничение частоты повторных уведомлений и отдельное уведомление о
  восстановлении.
- Состояния инцидента: open, acknowledged, resolved.
- Возможность подтвердить инцидент и записать действие администратора.
- Сбой доставки уведомления не должен останавливать сбор метрик и
  мониторинг.

**Пример уведомления:**

> Сервис: mado-bot.service
> Состояние: failed
> Время: UTC timestamp
> Причина: процесс завершился с ошибкой
> Действие: откройте карточку сервиса и последние логи.

## 6. Схема базы данных

Используется отдельная база `bot_control_center`. BCC не должен читать
или изменять таблицы HR-бота и других бизнес-приложений.

| Таблица | Назначение и основные поля |
|---|---|
| monitored_services | Реестр служб: id, name, unit_name, type, enabled, interval, config_json |
| service_status_history | История статусов: service_id, status, pid, observed_at, details_json |
| incidents | Инциденты: service_id, fingerprint, severity, status, first_seen, last_seen, resolved_at |
| log_events | Выбранные события: service_id, source, level, message, event_time, fingerprint |
| users | Веб-пользователи: username, password_hash, role, is_active |
| user_sessions | Активные сессии, срок действия и отзыв |
| telegram_admins | Разрешённые Telegram ID и статус доступа |
| notification_settings | Каналы, типы событий, получатели и cooldown |
| notification_deliveries | Результат и время доставки уведомлений |
| server_metrics | Выбранные метрики CPU, RAM, диска и uptime |
| health_checks | Результаты проверок зависимостей |
| audit_logs | Кто, что, когда и с каким результатом сделал |

### Связи

- `monitored_services` 1:N `service_status_history`
- `monitored_services` 1:N `incidents`
- `monitored_services` 1:N `log_events`
- `incidents` 1:N `notification_deliveries`
- `users` 1:N `user_sessions`

## 7. REST API (`/api/v1`)

| Метод | Путь | Назначение |
|---|---|---|
| GET | /healthz | Доступность процесса и состояние БД |
| POST | /auth/login | Авторизация |
| POST | /auth/logout | Завершение сессии |
| GET | /dashboard/summary | Сводка по системе |
| GET | /services | Список служб |
| GET | /services/{id} | Детали службы |
| GET | /services/{id}/history | История статусов |
| GET | /services/{id}/logs | Логи с фильтрами |
| GET | /incidents | Список инцидентов |
| POST | /incidents/{id}/acknowledge | Подтверждение инцидента |
| GET | /metrics/server | Метрики VPS |
| GET | /notifications/settings | Настройки уведомлений |
| PATCH | /notifications/settings/{id} | Изменение настроек |

### Требования к API

- Пагинация и ограничения размера ответа; валидация всех фильтров.
- Единый формат ошибок с request_id и безопасным сообщением.
- Запрет произвольных путей, shell-команд и неизвестных unit-имён в
  запросах логов.
- Rate limiting, журналирование административных действий и отсутствие
  секретов в ответах.
- Health endpoint не раскрывает конфигурацию, пароли или строки
  подключения.

## 8. Безопасность

BCC получает доступ к чувствительным сведениям о сервере и логам, поэтому
безопасность должна быть реализована до внешнего открытия панели. Полный
список принципов и ролей — в [`security.md`](security.md).

### Процессы

- `bcc-api.service` — REST API для веб-панели.
- `bcc-worker.service` — мониторинг, метрики, обработка инцидентов и
  очередь уведомлений.
- `bcc-adminbot.service` — Telegram Admin Bot.

Для служб предусмотрены `Restart=on-failure`, отдельный пользователь,
ограничения ресурсов и systemd hardening-параметры (см.
`deploy/systemd/*.service`). Совместимость ограничений нужно проверить с
механизмом доступа к journald.

## 10. План реализации

**Этап 1 — аудит и подготовка**
- Инвентаризация systemd, PM2, портов, Nginx, PostgreSQL и каталогов
  (`deploy/scripts/audit_server.sh`).
- Резервная копия конфигураций и проверка свободного места.
- Создание отдельного пользователя, БД и allowlist служб
  (`deploy/scripts/create_user_and_db.sh`).

**Этап 2 — backend и сбор данных**
- FastAPI, модели, миграции и тесты.
- Чтение статусов systemd и разрешённых журналов.
- Сбор CPU/RAM/диска/uptime, история статусов и инциденты.

**Этап 3 — веб-панель**
- Авторизация, сводка, карточки служб, фильтры логов и инцидентов.
- Обработка ошибок, пагинация, роли и аудит.

**Этап 4 — Telegram Admin Bot**
- Allowlist Telegram ID и команды статуса.
- Уведомления о подтверждённом сбое и восстановлении.
- Дедупликация, cooldown и обработка ошибок доставки.

**Этап 5 — развёртывание и испытания**
- Nginx, HTTPS, systemd-службы BCC и контроль доступа.
- Симуляция падения тестового сервиса и восстановления.
- Проверка перезагрузки VPS, резервных копий и очистки данных.

## 11. Развёртывание

Подробная инструкция — в [`deployment.md`](deployment.md).

| Объект | Рекомендуемое размещение |
|---|---|
| Проект | /opt/bot-control-center/ |
| Backend | /opt/bot-control-center/backend/ |
| Frontend build | /opt/bot-control-center/frontend/dist/ |
| Файл секретов | /etc/bot-control-center/bcc.env |
| База данных | Отдельная PostgreSQL DB: bot_control_center |
| Системные логи | journalctl -u bcc-api.service и другие службы BCC |
| Веб-адрес | Отдельный поддомен, например bots.example.com |

> Критическое ограничение: развёртывание BCC не должно требовать
> остановки существующих mado-bot.service, invitebot.service,
> bkbot.service и tgbot.service. До завершения испытаний не менять их
> unit-файлы, окружение, порты и базы данных.

## 12. Критерии приёмки

1. Все разрешённые systemd-службы отображаются с корректным статусом.
2. После падения тестовой службы статус обновляется в пределах 30 секунд
   при штатном цикле мониторинга.
3. Веб-панель показывает последние логи без доступа к произвольным
   файлам.
4. После подтверждённого сбоя приходит Telegram-уведомление.
5. После восстановления приходит отдельное уведомление.
6. Повторяющиеся ошибки не создают бесконечный поток сообщений.
7. CPU, RAM, диск и uptime отображаются корректно.
8. Неавторизованный пользователь не получает данные API.
9. Секреты и токены отсутствуют в API-ответах и интерфейсе.
10. Перезапуск BCC не останавливает существующих ботов.
11. После перезагрузки VPS мониторинг автоматически запускается.
12. Настроены резервное копирование и очистка старых данных.

## 13. Риски и меры снижения

| Риск | Мера |
|---|---|
| Слишком широкие права к journald | Allowlist служб, минимальные права, фильтрация на сервере |
| Ложные тревоги при кратком сбое | Порог подтверждения, cooldown, дедупликация |
| Процесс жив, но бот не отвечает | Отдельный heartbeat / health check |
| Переполнение БД логами | Хранить только выбранные события, TTL и лимиты |
| Раскрытие токенов в traceback | Маскирование, фильтрация, ограничение доступа |
| BCC влияет на рабочие приложения | Изоляция процессов и отсутствие изменений существующих unit |
| Сбой Telegram API | Очередь/повтор доставки с ограничением попыток |

## 14. Рекомендуемый порядок работ

Начать с аудита VPS и read-only мониторинга systemd/journald. Затем
подключить веб-панель, после чего Telegram Admin Bot и уведомления.
Управление запуском и остановкой сервисов, автоматические исправления и
GitHub deployment добавлять только отдельным этапом после проверки
безопасности.
